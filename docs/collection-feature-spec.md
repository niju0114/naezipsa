# 저장 · 비교 · 컬렉션 설계

작성일 2026-09-10 · 상태 **설계 확정, 미구현**

프론트엔드·백엔드가 함께 보는 문서입니다.

---

## 1. 한 줄 요약

**저장은 저장이고, 비교는 비교고, 컬렉션은 정리다.** 셋을 완전히 분리합니다.

```
                    저장한 매물
                A B C D E F G H I        무제한
                  │           │
        ┌─────────┘           └──────────┐
        ▼                                ▼
   비교판 (최대 6)                    컬렉션
   A B C D E F                  강남권:  A C G H
                                20억↓:  B C I
```

매물 하나가 **비교판에 있든 없든, 컬렉션에 있든 없든 저장 목록에는 그대로 남습니다.**

---

## 2. 왜 이렇게 나누나

이전 설계는 *"매물은 비교판이나 컬렉션에 있으면 살아 있고, 둘 다에서 빠지면 삭제"* 였습니다.
그 규칙에는 문제가 있었습니다.

- **같은 버튼이 상황에 따라 다른 일을 합니다.** "빼기"를 눌렀는데 어떤 때는 보관되고
  어떤 때는 삭제됩니다.
- 사용자가 **"보존하려면 컬렉션에 넣어야 한다"** 를 학습해야 합니다.
- 프론트는 매번 경고창을, 백엔드는 매번 삭제/보관 판단을 해야 합니다.

셋을 분리하면 이 복잡도가 통째로 사라집니다.

| 행동 | 결과 | 되돌리기 |
|---|---|---|
| **비교에서 빼기** | 비교판에서만 빠짐. 저장 목록에 그대로 | 실행 취소 / 다시 올리기 |
| **컬렉션에서 빼기** | 그 컬렉션에서만 빠짐 | 다시 담기 |
| **삭제** | 데이터가 사라짐 | 없음 (확인 다이얼로그 필수) |

**"빼기"는 언제나 안전하고, "삭제"만 위험합니다.**

## 3. 세 가지 개념

| | 무엇 | 제한 | 성격 |
|---|---|---|---|
| **저장한 매물** | 관심 있어 기록해둔 모든 집 | 없음 | 수집 |
| **비교판** | 지금 집중해서 비교하는 매물 | **6개** | 의사결정 |
| **컬렉션** | 저장한 매물을 목적별로 묶기 | 없음 · 중복 가능 | 정리 |

### 왜 비교판만 6개인가

6개 제한은 **모으는 개수**가 아니라 **동시에 비교하는 개수**에 대한 것입니다.
모으는 건 많을수록 좋고, 비교는 적을수록 정확합니다.

- **Cowan (2001)** — 되뇌기 없이 작업기억에 붙들 수 있는 덩어리는 약 4±1개
- **Iyengar & Lepper (2000)** — 잼 시식 실험. 24종일 때 구매율 3%, **6종일 때 30%**
- **Hick's Law** — 선택지가 늘면 결정 시간이 로그 함수로 증가

매물 하나가 가격·평형·전세가율·거래량 등 **여러 축을 가진 덩어리**라 단순 선택보다
부담이 큽니다. 6은 2×3 격자로 떨어져 반응형 배치도 자연스럽습니다.

> 선택 과부하 연구는 조건에 따라 결과가 갈립니다(Scheibehenne 2010).
> "6이 유일한 정답"은 아니고 **4~7 범위 안의 근거 있는 값**입니다.

## 4. 화면 흐름

### 4-1. 매물 저장

```
[매물 카드]  래미안 84㎡ · 18억 5천
                      [저장하고 비교]  [저장만]
                            ↓
              저장 목록에 추가
              + 비교판에 빈칸 있으면 자동으로 올림
```

### 4-2. 비교판이 가득 찼을 때 — 막지 않고 교체를 제안

```
새 매물을 저장했습니다.
비교판이 가득 차 있습니다. 어떤 매물과 바꿀까요?

┌────────┬────────┬────────┐
│ 래미안  │  현대   │  자이   │
├────────┼────────┼────────┤
│ 롯데    │  힐스   │  푸르지오│
└────────┴────────┴────────┘
   ↑ 누르면 그 자리와 교체

              [ 일단 저장만 하기 ]
```

**저장은 언제나 성공합니다.** 비교판만 자리가 없을 뿐입니다.

### 4-3. 비교에서 빼기 — 확인 없이 즉시

```
[비교에서 빼기]
      ↓
┌────────┬────────┬────────┐
│   +    │  현대   │  자이   │
└────────┴────────┴────────┘

래미안을 비교에서 뺐습니다.  [실행 취소]
```

경고창이 없습니다. 저장 목록에 그대로 있으니 위험하지 않습니다.

### 4-4. 컬렉션 → 골라서 비교

컬렉션이 12개여도 한꺼번에 비교판에 올리지 않습니다.

```
강남권 (12)

☑ 래미안   18.2억
☑ 자이     19.1억
☑ 현대     17.8억
☐ 롯데     20.4억
☐ ...
                    [ 선택한 3개 비교하기 ]
```

**컬렉션은 계속 커져도 됩니다.** 비교는 그중 2~6개만 고릅니다.

### 4-5. 삭제 — 유일하게 위험한 동작

```
[⋯] → 저장 목록에서 삭제

"래미안 84㎡를 삭제합니다.
 비교판과 컬렉션 2곳에서도 함께 사라집니다.
 이 동작은 되돌릴 수 없습니다."
        [ 삭제 ]   [ 취소 ]
```

컬렉션을 삭제할 때는 **매물을 지우지 않습니다.** 묶음만 없어집니다.

```
"강남권 컬렉션을 삭제합니다.
 안에 있던 매물 12개는 저장 목록에 그대로 남습니다."
```

## 5. 비교판 — 여기가 제품의 핵심입니다

저장·정리는 수단이고, 사용자의 진짜 질문은 **"그래서 이 중에 뭐가 제일 낫지?"** 입니다.
6개를 카드로 나열만 하면 그 질문에 답하지 못합니다.

### 5-1. 비교표

같은 축을 나란히 놓고 **가장 나은 값을 강조**합니다.

| | 래미안 | 현대 | 자이 |
|---|---:|---:|---:|
| 내 호가 | 18.5억 | **17.8억** | 19.1억 |
| 최근 대표가 | 18.2억 | 17.9억 | 18.3억 |
| 호가 괴리 | +1.6% | **-0.6%** | +4.4% |
| 평단가 | 5,430만 | **5,240만** | 5,610만 |
| 전세가율 | 48% | **53%** | 44% |
| 3년 거래 | 14건 | **21건** | 8건 |

**계산에 필요한 값은 이미 다 있습니다** — `metrics`(대표가·평단가·전세가율·거래량)와
사용자의 `list_price`로 호가 괴리율까지 나옵니다.

### 5-2. 자동 인사이트

이미 만들어둔 AI 분석(`POST /api/v1/dashboard/insight`)이 비교 근거를 문장으로 냅니다.

> 현대는 세 후보 중 호가가 가장 낮고 거래량이 가장 많습니다.
> 자이는 최근 대표가 대비 호가가 4.4% 높습니다.
> 래미안은 두 후보 사이의 균형형에 가깝습니다.

**비교판 안에 이걸 넣으면 "아카이빙 → 비교 → 의사결정" 흐름이 완성됩니다.**

## 6. 테이블 설계

```
saved_items                  저장한 매물 (기존 dashboard_items 대체)
  id              BIGSERIAL PK
  user_id         UUID       → profiles.id
  size_id         BIGINT     → size_master.id
  on_compare      BOOLEAN    true 인 것만 비교판에. 사용자당 최대 6
  list_price      BIGINT     호가. 단위 원
  floor           INT
  dong, ho        VARCHAR(20)
  direction       VARCHAR(10)
  interior_state  VARCHAR(20)
  status          VARCHAR(20)
  memo            VARCHAR(500)
  created_at, updated_at

collections                  컬렉션
  id              BIGSERIAL PK
  user_id         UUID       → profiles.id
  name            VARCHAR(30)
  memo            VARCHAR(200)
  created_at

collection_items             컬렉션 ↔ 매물 (N:M)
  collection_id   BIGINT     → collections.id      ON DELETE CASCADE
  saved_item_id   BIGINT     → saved_items.id      ON DELETE CASCADE
  created_at
  PRIMARY KEY (collection_id, saved_item_id)
```

**인덱스**

- `saved_items (user_id, on_compare)` — 비교판 조회가 가장 잦음
- `collection_items (saved_item_id)` — "이 매물이 어느 컬렉션에 있나" 역조회

**CASCADE 방향에 주의**

- 컬렉션 삭제 → `collection_items` 만 지워짐. **매물은 남습니다**
- 매물 삭제 → 모든 컬렉션에서 자동으로 빠짐

### `on_compare BOOLEAN` 을 쓰는 이유

슬롯 번호(`compare_slots` 테이블, `slot 1~6`)도 후보였으나 두 가지 이유로 택하지 않았습니다.

1. **슬롯 번호는 순서를 내포합니다.** 팀 규칙이 *"표시 순서는 백엔드에서 관리하지 않는다"*
   인데, 프론트에 이미 드래그 정렬(`useDragReorder.js`)이 있어 슬롯 번호와 어긋납니다.
2. **빈 칸 상태**가 생깁니다. `slot 1`은 찼고 `slot 2`는 비었는데 `slot 3`은 찬 상황을
   허용해야 하고, 앞으로 당길지 그대로 둘지 규칙이 하나 더 필요합니다.

슬롯이 주는 이점(원자적 교체)은 아래 **교체 API** 하나로 얻습니다.

### 기존 데이터

`dashboard_items` 는 현재 **0행**입니다. 이관 비용이 없으니 지금이 바꾸기 가장 좋은 시점입니다.

## 7. API 명세

모두 **로그인 필요**. 남의 매물·컬렉션은 조회·수정·삭제 불가(404).

### 7-1. 저장한 매물

| ID | 메서드 | 경로 | 설명 |
|---|---|---|---|
| S-01 | GET | `/api/v1/saved-items` | 저장 목록 (무제한) + 지표 + 소속 컬렉션 |
| S-02 | POST | `/api/v1/saved-items` | 매물 저장. 비교판에 빈칸 있으면 자동 등록 |
| S-03 | GET | `/api/v1/saved-items/{id}` | 상세 |
| S-04 | PATCH | `/api/v1/saved-items/{id}` | 선택정보(호가·층·동·호·향·인테리어·메모) 수정 |
| S-05 | PATCH | `/api/v1/saved-items/{id}/status` | 상태 변경 |
| S-06 | DELETE | `/api/v1/saved-items/{id}` | **진짜 삭제.** 비교판·컬렉션에서도 사라짐 |

**S-02 응답** — 비교판에 올랐는지 알려줍니다.

```json
POST /api/v1/saved-items
{ "size_id": 657, "list_price": 1850000000, "dong": "101" }

→ 201 { "id": 12, "on_compare": true,  "compare_count": 4, "compare_max": 6 }
→ 201 { "id": 12, "on_compare": false, "compare_count": 6, "compare_max": 6 }
                                        ↑ 가득 참. 프론트가 교체 UI를 띄움
```

### 7-2. 비교판

| ID | 메서드 | 경로 | 설명 |
|---|---|---|---|
| C-01 | GET | `/api/v1/compare` | 비교판 매물 + 지표 |
| C-02 | POST | `/api/v1/compare/items` | 비교판에 올리기 |
| C-03 | DELETE | `/api/v1/compare/items/{id}` | 비교판에서 빼기 (**저장 목록엔 남음**) |
| C-04 | POST | `/api/v1/compare/swap` | **교체** — 하나 내리고 하나 올리기 |

```json
POST /api/v1/compare/items
{ "item_id": 31 }
→ 200
→ 409  비교판이 이미 6개  { "error": { "code": "CONFLICT", ... } }

POST /api/v1/compare/swap
{ "out_item_id": 12, "in_item_id": 31 }
→ 200  한 트랜잭션에서 처리. 중간에 5개가 되는 순간이 없음
```

### 7-3. 컬렉션

| ID | 메서드 | 경로 | 설명 |
|---|---|---|---|
| L-01 | GET | `/api/v1/collections` | 컬렉션 목록 + 매물 수 |
| L-02 | POST | `/api/v1/collections` | 생성 |
| L-03 | PATCH | `/api/v1/collections/{id}` | 이름·메모 수정 |
| L-04 | DELETE | `/api/v1/collections/{id}` | 삭제 (**매물은 안 지움**) |
| L-05 | GET | `/api/v1/collections/{id}/items` | 안의 매물 + 지표 |
| L-06 | POST | `/api/v1/collections/{id}/items` | 담기 |
| L-07 | DELETE | `/api/v1/collections/{id}/items/{item_id}` | 빼기 |

### 7-4. 매물 응답 공통 형태

`saved-items` · `compare` · `collections/{id}/items` 가 모두 같은 모양을 씁니다.

```json
{
  "id": 12,
  "size_id": 657,
  "status": "considering",
  "on_compare": true,

  "list_price": 1850000000,
  "floor": 12, "dong": "101", "ho": "1203",
  "direction": "south", "interior_state": "partial", "memo": null,

  "complex_name": "래미안대치팰리스",
  "legal_dong_name": "대치동",
  "build_year": 2015,
  "representative_area": 84.97,
  "pyeong": 34,

  "metrics": {
    "recent_median_price": 1820000000,
    "min_price": 1650000000,
    "max_price": 2010000000,
    "price_per_pyeong": 54300000,
    "trade_count_3y": 14,
    "last_trade_date": "2026-07",
    "jeonse_ratio": 48.2
  },

  "collections": [
    { "id": 1, "name": "강남권" },
    { "id": 3, "name": "예산 20억 이하" }
  ],

  "created_at": "2026-09-10T09:00:00Z",
  "updated_at": "2026-09-10T09:00:00Z"
}
```

금액은 전부 **원 단위**입니다 (18.5억 → `1850000000`).
지표가 아직 계산되지 않은 평형은 `metrics`가 `null`입니다.

### 7-5. 오류 코드

기존 형식 그대로: `{"error": {"code": ..., "message": ..., "details": ...}}`

| 코드 | 언제 |
|---|---|
| 401 | 토큰 없음/만료/위조 |
| 404 | 없는 매물·컬렉션, 또는 남의 것 |
| 409 | 비교판 6개 초과 / 이미 담긴 매물을 또 담음 |
| 422 | 허용값 아님 (이름 길이, status, direction 등) |

## 8. 기존 A-01~A-09 와의 관계

경로가 바뀝니다. **프론트가 아직 A쪽 API를 붙이지 않았으므로 지금이 바꿀 시점입니다.**

| 기존 | 새 경로 | 비고 |
|---|---|---|
| A-03 `POST /dashboard/items` | `POST /saved-items` | 6개 초과여도 **저장은 성공** |
| A-04 `GET /dashboard/items` | `GET /compare` (비교판) / `GET /saved-items` (전체) | **두 개로 갈림** |
| A-05 `GET /dashboard/items/{id}` | `GET /saved-items/{id}` | |
| A-06 `PATCH .../details` | `PATCH /saved-items/{id}` | |
| A-07 `PATCH .../status` | `PATCH /saved-items/{id}/status` | |
| A-08 `DELETE /dashboard/items/{id}` | `DELETE /saved-items/{id}` (삭제) / `DELETE /compare/items/{id}` (빼기) | **두 개로 갈림** |
| A-09 `GET /dashboard` | `GET /dashboard` | **유지.** 프로필 + 비교판 + 컬렉션 요약 |
| AI-01 `POST /dashboard/insight` | 유지 | 비교판 기준으로 분석 |

**A-04와 A-08이 각각 둘로 갈리는 게 이번 변경의 핵심**입니다. 하나의 엔드포인트가
두 가지 의미를 겸하던 것을 나눈 것입니다.

## 9. 프론트엔드 체크리스트

- [ ] 매물 카드에 **`[저장하고 비교]` / `[저장만]`** 두 버튼
- [ ] 비교판 가득 찼을 때 **교체 UI** (6칸 그리드에서 바꿀 대상 선택)
- [ ] 비교에서 빼기는 **확인 없이 즉시** + "실행 취소" 토스트
- [ ] 삭제만 확인 다이얼로그 — "비교판과 컬렉션 N곳에서도 사라집니다"
- [ ] 매물 카드에 **컬렉션 뱃지** (`item.collections`)
- [ ] 컬렉션 상세에서 **체크박스로 골라 `[선택한 N개 비교하기]`**
- [ ] 컬렉션 삭제 시 "매물은 저장 목록에 남습니다" 안내
- [ ] **비교표** — 축별 최우수 값 강조
- [ ] 비교표 아래 **AI 인사이트** (`POST /dashboard/insight`)
